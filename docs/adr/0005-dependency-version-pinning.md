# Pin dependency edges to accepted versions; gate revalidation on interface, not text

**Status**: accepted

ADR-0004 established that `potentially-stale` propagates through the dependency graph whenever an ancestor's accepted version moves on, but left open how a dependency edge knows which version it was checked against, and what a downstream node must do once it has. Answering that (issue #12) fixes four rules.

**Rule 1 — Imported result nodes are immutable.** The `ReferenceRecord` a node cites (a paper, book, arXiv entry) can still be freely re-reviewed — its `review_status`/`trust_level` change over time, that's ordinary Reference review. But the Imported result node itself — the specific mathematical claim pulled in from that source (its statement, `source_locator`, `source_version`) — never changes in place. If the cited source is corrected, retracted, or reinterpreted, that produces a *new* Imported result node; dependents migrate to it deliberately, they don't inherit the correction silently.

**Rule 2 — dependency edges pin an accepted version.** For a local node (Theorem/Lemma/Claim), a dependency edge pins the specific Candidate-proof version that was current and Accepted when the edge was checked: `M → L7@v3`, reusing the Candidate-proof version numbers from ADR-0003 rather than inventing a second counter. For an Imported result, the edge just pins the node's id (`M → IR17`) — no version needed, because Rule 1 already makes the node itself the immutable identity.

**Rule 3 — what a dependency needs to be re-checked against isn't its text, it's its accepted mathematical interface.** `L7`'s statement, assumptions, and mathematical scope are its interface; its internal proof, proof strategy, and Evidence checks are not — a dependent never actually relies on *how* `L7` was proved, only on *what* it says. So: when `L7` advances to a new accepted version, compare interfaces.
- **Interface unchanged** (only the internal proof or its evidence changed): a Human Review confirms the existing Candidate proof remains valid and updates the dependency edge's pin — no new Candidate proof is written. This is **Lightweight re-review** (`dependency_revalidation`, see below): it revalidates a dependency, it does not touch the reviewing node's own acceptance state, which was never in question.
- **Interface changed**: the old Candidate proof no longer demonstrably accounts for the new premise, so a new Candidate-proof version is required against the new interface — even if, in the end, its text turns out identical to the old one. The point isn't the words; it's that someone looked at the new interface and re-affirmed the argument holds under it.

**Rule 4 — opening a Challenge is permissive; resolving one is Human-Review-only.** Any agent or collaborator may open a Challenge against an already-Accepted node — local or Imported result — since raising a concern is not a mathematical judgment ("this deserves a second look," not "this is wrong"), so it needs no gate, the same reasoning ADR-0002/CONTEXT.md's Split already applies. Only Human Review resolves one: dismissing it, accepting a revised Candidate proof, issuing `revision_requested`/`rejected`, or — when the target is an Imported result — deciding the Reference-review question (trust the citation as-is, or treat it as no longer callable and let dependents migrate under Rule 1). Lightweight re-review is itself a Human Review action, but note what it changes: dependency pins and integrity provenance, never acceptance state, which stays governed solely by ADR-0004's Invariant 1.

**Recording it**: `ReviewRecord` (ADR-0002) gains a `kind` — `acceptance`, `reference_review`, `evidence_review`, or `dependency_revalidation` — so a Lightweight re-review is never confused with a fresh Acceptance. Its decision value is `reaffirmed`, not `approved`: `kind=dependency_revalidation, decision=reaffirmed, target=M, dependency=L7, old_pin=v3, new_pin=v4, rationale=...`. Appending that record and updating the edge's pin from v3 to v4 must happen as one atomic write — an edge pinned to v4 with no matching record, or a record with no matching pin update, is an inconsistent state, not a valid intermediate one.

**This is what actually clears `potentially-stale`.** Nothing un-sets a flag: `potentially_stale(v)` (ADR-0004, point 4) is computed by reachability from every open Challenge's target *and* every edge whose pin lags its target's current accepted version. Once a Lightweight re-review (or a new, Accepted Candidate proof) brings every one of a node's edges back to current, and no open Challenge is reachable, the same query simply stops returning true for it — nothing is cleared by hand, and nothing can be left half-cleared.

This is hard to reverse in the same way ADR-0003 was: once dependency edges carry version pins that reviews and staleness both key off, collapsing back to bare `M → L7` references would silently lose the distinction this ADR exists to make — between "this dependency is current" and "this dependency was fine as of a version that's since moved on."
