# Only Human Review changes acceptance; everything else derives integrity signals

**Status**: accepted

Auditing the peripheral modules against the graph model (issue #3, issue #9) surfaced a real violation of "human-in-the-loop": `verify accept` (`verification_results.py::_update_obligation`) directly closes or blocks a `ProofObligation` and mutates trust-sensitive project state, with no researcher decision in the loop. Nothing stopped an automated checker from silently deciding a result was established. Left as-is, the new graph model would inherit the same hole the moment any checker, checklist, or future automation touched a node.

Decided: one invariant governs every subsystem going forward.

1. **Human Acceptance Authority.** Only a Human Review decision may set or change a proof map node's `accepted`, `rejected`, or `revision_requested` acceptance state. No checker, checklist, checker-derived recommendation, or automated process may do so, however confident its output.
2. **Three-axis node state.** A node's state is never folded into one flat status. It is tracked along three independent axes: **workflow state** (open/claimed/review-needed/revision-requested/blocked — how far the current attempt has gotten, ADR-0002), **acceptance state** (unreviewed/accepted/rejected — set only by Human Review), and **integrity state** (current/potentially-stale/challenged — a derived warning overlay). This refines ADR-0002's single derived-status model into three axes shown together, rather than one value competing for a single display slot; ADR-0002's underlying principle — nothing is stored, everything is computed from lower-level records — still holds for all three.
3. **Challenge semantics.** A Challenge is a claim raised against an already-Accepted node that its acceptance may no longer hold. Opening a Challenge sets that node's own integrity state to `challenged`; it never changes the node's acceptance state. Only Human Review resolves a Challenge, either by dismissing it or by revising the node and re-Accepting it.
4. **Transitive integrity propagation.** Any node reachable (via dependency edges) from an open Challenge's target, or from a target whose currently-accepted Candidate-proof version has moved past the version a dependent's edge was checked against, is `potentially-stale` if it is itself Accepted — displayed as "Accepted · Potentially stale" — or shows the same underlying cause as Blocked (labelled `dependency-challenged`) if it is not yet Accepted. This propagates across the whole reachable subgraph, not just one hop: a trust problem anywhere upstream is a reason to look, all the way downstream. It is computed by graph reachability from the set of open Challenges' targets and version-mismatched edges — `potentially_stale(v) ⟺ ∃ open challenge c, c.target ⤳ v` — never written per node. Dismissing a Challenge, or reconfirming a dependency against a node's new accepted version, therefore clears every `potentially-stale` it alone caused automatically; nothing needs manual cleanup.
5. **Evidence non-authority.** An Evidence check (what `verify` becomes) is an automated or semi-automated check run against a specific Candidate proof, recorded as `passed`/`failed`/`inconclusive`/`error`/`stale`. Human Review may judge a given Evidence check `trusted` or `unusable` — a judgment about whether the check itself is credible — but an Evidence check can never close an obligation, block one, or grant/revoke acceptance. `verify accept`/`verify reject`, which do exactly that today, are removed.

Point 4 does not reopen ADR-0002's rule that `blocked` never overrides `accepted`/`rejected` in what's displayed — that rule was, and remains, about ordering *within* the workflow axis. `Potentially-stale` is not a workflow-axis value and does not compete with `accepted` for the same display slot; it is a second, independent axis shown alongside it. The two ADRs do not conflict.

A Challenge's own record needs no new bibliography of parallel concepts: an ordinary observation about a node that doesn't call its acceptance into doubt is just a `CommentThread` (already generic over `object_type`/`object_id`, ADR-0001); only the invalidating case — "this specific accepted result may not hold" — gets the new, structural Challenge object with its own resolution workflow.

This is hard to reverse once agents and researchers rely on Evidence checks as advisory-only: any future erosion back toward "a trusted checker can auto-accept" would have to be a deliberate, visible reversal of this ADR, not a quiet feature addition.
