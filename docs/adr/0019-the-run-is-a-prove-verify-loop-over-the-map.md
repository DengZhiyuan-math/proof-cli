# The run is a prove–verify loop, and the map is the agents' blackboard

**Status**: proposed (drafted 2026-10-04; to be decided in an issue). Amends ADR-0016 points 1, 2 and 4: a run has a fourth role, the Verifier, whose passing verdict is the agent's gate to request review; a run keeps a record of its attempts and briefs each turn from it; and a run on a Theorem may be a coordinator over the Theorem's subtree. ADR-0004, ADR-0009 and ADR-0010 stand untouched: no role, no verdict and no coordinator makes a Review decision, and only the researcher changes acceptance. ADR-0018 stands: all of this is the proof-agents package, against `RunHooks` and the agent manager.

## Context

ADR-0016 made the Proof agent autonomous: one run per node, three roles in turn, started once and watched. In use three things are missing, and one of them is a hole in the trust boundary this system exists to manage.

1. **Nothing reads the proof against the Prover.** The Prover writes a draft, the Typesetter writes it down, and the same Prover requests review. The Numerics role records Evidence checks, but those are computations, not a reading of the argument. The researcher is the first adversarial reader of every proof, and so the researcher is the bottleneck — exactly the gap Cogentic (Cai et al., arXiv:2609.40324) names in its discussion: a harness "can produce candidate results faster than they can be read".
2. **A run forgets what it tried.** The next turn's prompt carries only the last hand-off note. After a context loss, or after Stop and Start, a new Prover walks the same dead end. Our principle is local-state-first; the run's own history is the one piece of state we did not persist in a form a later turn can use.
3. **Runs on sibling nodes do not know of each other.** The map has explicit dependencies, but two Claims under the same Lemma, with no edge between them, are often proved by the same technique, blocked by the same obstruction, or need the same auxiliary fact. Nothing today lets one run's finding reach the other, and nothing stops a run from quietly relying on a sibling's unaccepted proof if it happened to read the file.

Cogentic shows one answer that works on research-level problems: an orchestrator allocates independent provers across directions, every draft meets adversarial verifiers ("every step is wrong until justified, every citation incorrect until checked"), confirmed fragments are rewritten as self-contained lemmas and re-verified in isolation, a record keeps each attempt by what it tried to establish, the method and the objection it failed on, and briefings are summarised from that record for each prover. Its ledger of verified lemmas is promoted by the machine; ours cannot be, by ADR-0004.

For how parallel agents share, the mature designs agree on the shape rather than the mechanism: workers do not message each other. Anthropic's research system has subagents report only to a lead, synchronously; MetaGPT's agents publish structured messages to one shared pool and subscribe by role; PatchBoard restricts shared state to schema-grounded, path-authorised mutations because free-form shared context mixes "verified facts with unresolved repair attempts" and downstream agents then treat the latter as the former; AgentRoom gives concurrent coding agents file-level claims, an append-only broadcast log and each agent's status, and finds that "coordination, not parallelism or CRDT-merge, bears the load". The human precedent is the Equational Theories Project: one Lean repository as the only ground truth, an automatically derived implication graph as the dashboard, one claim per task, and partial results shared only by being formalised. Our proof map already is that blackboard — project state in SQLite, events, fog, memory, Evidence checks, one assignee per node — with the Accepted nodes as the ledger. What it lacks is the reading side: who reads what, when, and what they may do with it.

## Decision

### A. The Verifier, and a verdict as the agent's gate

1. **A fourth role, the Verifier.** It reads the node's working proof as it stands — `proof.tex` and what it inputs, or a computation node's program and `out/` — against the node's statement and its dependencies' statements, adversarially: every step is unjustified until it is justified by the text or by a dependency it names, every appeal to a dependency is wrong until the dependency's statement actually gives it, every appeal to the literature is unchecked until it is read. It does no mathematics of its own beyond what checking requires, writes no file in the node folder except under `scratch/verifier/`, never splits, never requests review, and never makes a Review decision.
2. **Its output is a verdict, in the work log.** `proof node progress <node> --verdict passed|failed --note "<objections>"` records a `verdict` event: the outcome, the objections (numbered, each naming the step or the citation it attacks), the role, the agent name, and the SHA-256 of the working inputs the Verifier read, computed the way a Review snapshot's manifest is. A verdict is about one state of the files; a later edit makes it stale by construction.
3. **A passing verdict is the agent's gate to request review.** The Prover may run `proof node request-review` only when the newest verdict is `passed` and its hash is the current working inputs'. The run enforces this where a backend can: the Prover's turn is given the `request-review` permission only then (Claude Code), and the brief says the same where it cannot (Codex), as ADR-0011 and ADR-0016 already treat scope. The gate is on the agent's request, not on the researcher's: Review what it has, and a researcher's own request-review on the node page, freeze a snapshot regardless of any verdict, as today.
4. **The run records a passing verdict as an Evidence check on the snapshot it gated.** An Evidence check is against a Candidate proof, which exists only once a snapshot is frozen; the verdict was made before. So when a review request ends the run, the run itself — not a role — compares the new snapshot's manifest hash with the gating verdict's and, when they agree, records `proof node evidence record <candidate-proof-id> passed --run-by <agent name>/verifier --notes "<the verdict's note>"`. When they disagree nothing is recorded and the work log says why. The Evidence check is advisory, as ADR-0004 says every Evidence check is; what it gives the researcher is that the proof they are asked to read has been read against, and by whom.
5. **A failing verdict returns the work to the Prover** with the objections as the next turn's briefing (part B). An objection the Verifier cannot settle because it concerns an Accepted dependency's own proof is a Challenge, which the Verifier may open (`proof challenge open`), as any agent may.
6. **The order of roles.** A run's default cycle is Prover → (Numerics, Typesetter, as handed off) → Verifier → Prover. The Verifier is handed to by the Prover when it believes the draft is complete, and the run brings the Verifier back after every Typesetter turn that changed a `.tex` file, since what will be frozen is the LaTeX, not the draft. A single role may still be started on its own, the Verifier included: Start → Verifier on a node whose proof the researcher wrote is a legitimate use.

### B. The record, and briefings built from it

7. **An attempt is recorded by what it tried to establish, how, and what it failed on.** When the Prover abandons a line, it closes it: `proof node progress <node> --attempt "<the claim or step it was after>" --method "<the approach>" --failed-on "<the objection or obstruction>"`, an `attempt` event in the work log. A failing verdict's objections and the stuck notes of every role count as attempts too, recorded by the run from the events it already has. The record is insert-only, like the rest of the work log.
8. **What is learned, as against what was tried, goes to memory with its existing types.** A dead end that would mislead another node is a memory entry with `--status failed`; a technique that worked, `--status tactic`; an observation not yet trusted, `--status tentative`; each scoped to the node (`--node-id`), tagged with the role and agent name through `--source`. No new memory kind is added: the layers and statuses memory already has are the typed channel. The Proof fog stays what CONTEXT.md says it is — things still to think through, not a record of what was learned.
9. **Every turn begins with a briefing, built by the run, not by the role.** Before a turn the run assembles, in a fixed order and within a fixed size: the node's statement and its dependencies' statements with their key ideas when Accepted; the researcher's redirect, if any; the last hand-off or report; the open objections of the newest verdict; the node's attempts, newest first; the diff of the working inputs since the last turn's end, when one exists (part D); and the shared entries part C allows, each marked with the node and role it came from and with *unverified* unless it is an Accepted node's statement. The role reads the briefing and may read further; it does not have to reconstruct the history from the work log. Two turns may be briefed from the same record differently — a Verifier is given the objections and the dependencies' statements first, a Prover the attempts first — which is the one place Cogentic's "different readings of the same history" survives in a sequential run.
10. **The auditor is the Verifier and the Prover together, and the ledger is the map.** When a verdict fails the proof but its note confirms a step as justified and self-contained, the Prover may split that step out as a Claim (`proof node split`, ungated as ever), the run starts a run on the Claim whose first turn is a Verifier on the split-out text, and the Claim is requested for review when it passes. Promotion into the ledger is that Claim's Acceptance, by the researcher; until then the parent is Blocked on it, as any parent is. Nothing else promotes anything: a confirmed fragment that is not split out is a note in the verdict, nothing more.

### C. Sharing across nodes: the map is the blackboard

11. **Results are shared only through the DAG.** A fact one node's run establishes and another node needs is a Claim both depend on, never a sentence copied into the other node's briefing or proof. The briefing marks every sibling's text as unverified, and the Verifier treats an appeal to a sibling's unaccepted proof as an appeal to nothing. This is the Equational Theories Project's rule — a result exists when it is in the repository — applied to a map whose repository is the Accepted nodes.
12. **Methods, obstructions and dead ends are shared through memory**, by the typed entries of point 8, and only those. A run may read any node's memory; it may write only its own node's.
13. **Progress is shared through what already exists**: the node's assignee (the claim) and its work log's plan and steps. A sibling's briefing may say "node B is on step 3 of 5, induction on n, and its last verdict failed on the base case" because all of that is project state already.
14. **The subscription rule.** A node's briefing draws shared entries from three sources, in this order and bounded: its dependencies and its dependents; its siblings, meaning the other children of each node it is a dependency of; and `proof retrieve` on the node's statement, for memory elsewhere in the map. Newest first, a fixed count each, the whole briefing under a fixed size. Nothing is pushed to a running turn.
15. **Ownership does not cross nodes.** A run edits only its node's files and dependency edges (the rules of `proof node depend` already refuse the rest). A run that has split out a Claim its sibling could use leaves the sibling a memory entry saying so; the sibling's Prover adds the edge, or does not.
16. **Sync points are turn boundaries.** A turn is one CLI job: it is briefed from the blackboard when it starts and its events are on the blackboard when it ends. The one exception is a Coordinator's redirect (point 19) when a node a running node depends on is Accepted, which reuses the researcher's Redirect channel and is read at the next turn as a redirect is.
17. **What is not done.** No agent-to-agent messages; no shared free-text scratch file across nodes; no role may cite a node's unaccepted proof as a fact; no advisor role rewrites the briefs or the allocation on its own — a pattern the record shows (the same objection three times, the same dead end on two nodes) is surfaced in the work log as a suggested redirect for the researcher, who decides.

### D. The Coordinator, the Decomposer, and the researcher's edits

18. **A Coordinator works a Theorem's subtree.** Started on a Theorem or Lemma from the map, it holds no node and takes no turn. It starts node runs on the frontier within the subtree, up to `[studio] parallel` at a time (default 2), builds their briefings (point 9), restarts a node's run after a failed verdict until the node's budget is spent, and, when every child is Accepted, starts the parent's own run for the proof that combines them. It never requests review itself, never Accepts, and stops when the subtree's root is requested for review, when its budget — the sum of the node budgets it may spend — is spent, or when every open node in the subtree is stuck. Its researcher actions are Start, Pause (no new node run begins; running ones finish their turn), Resume, and Stop and release (every node run it started is released). It is the only thing besides the researcher that starts a run.
19. **A Coordinator may redirect.** When a node in its subtree is Accepted it redirects the runs of that node's dependents with one line naming the Claim and its key ideas; this is the sole cross-node push, and it travels the existing Redirect channel.
20. **A Decomposer turn on a Theorem stops for the researcher.** Started as a single role on a Theorem with no children, the Decomposer reads the library and the literature first, writes the key theorems the course of the proof needs as a split into Claims, puts what it cannot yet state into the fog near the Theorem, and ends its turn with `--status needs-human --note "structure proposed; the researcher decides"` — a decision only a human can make, in ADR-0016's words, which is the step status the run already stops for. The researcher edits the map and, if they agree, starts a Coordinator. A split is ungated, so nothing stops a Prover from splitting mid-proof as today; what stops here is the shape of a whole research effort being set without a human reading it.
21. **The researcher's own edits are the strongest briefing.** At each turn's start the run compares the working inputs' hashes with those recorded at the previous turn's end. A difference not accounted for by a role's turn is the researcher's: its diff heads the next briefing as "the researcher changed …", the Verifier reads the changed steps as adversarially as any other, and the Prover does not revert them. No verdict is required for the researcher to request review on their own edits (point 3). This is the third layer of the system — the expert working in the LaTeX — made visible to the first two, which Cogentic has no counterpart for.

### E. What is deliberately not decided here

- **A population of Provers on one node.** Cogentic runs several provers on distinct directions in parallel. The latex-agent agent manager runs one job per studio and a node has one studio, so within a node directions are tried in sequence by one Prover and recorded as attempts; across nodes, parallelism is the Coordinator's. Several Provers on one node would need per-direction scratch folders and a second agent manager, and is left for a later decision.
- **The round verifier.** A verifier reading several drafts side by side needs several drafts at once; with one Prover per node it reads the current draft against the attempts, which is a weaker form of the same thing.
- **The verdict's grading.** A verdict is `passed` or `failed`; the objections carry the nuance. Cogentic does not say whether its verdicts are graded either.

## Consequences

- The researcher is no longer the first adversarial reader of every proof. What arrives for review carries a Verifier's Evidence check and its objections' history, and the key-ideas summary's 难点 can be written from them. Nothing about acceptance changes: an Evidence check is advisory, and a researcher may Accept a proof whose verdict failed or reject one that passed.
- A run survives Stop, Start and context loss with its attempts intact, and a node's work log becomes a record a person can read to see what was tried and why it did not work — which is also what the Decision's point 17 surfaces for them.
- Parallel runs on sibling nodes learn from each other through memory and the DAG, and through nothing else. The cost is that a useful fact must be stated as a Claim before another node may use it; that cost is the trust boundary, paid where it belongs.
- `proof node progress` grows `--verdict`, `--attempt`, `--method`, `--failed-on`; the work log gains `verdict` and `attempt` events; `proof.toml` gains `[studio] parallel` and a budget for a Coordinator. `AgentRole` gains `verifier` and `decomposer`. `RunHooks` grows what the run needs to compute input hashes, read sibling and dependency state, and record an Evidence check; the agent manager interface is unchanged. Everything a role does remains a `proof` command a human could run.
- Three-layer vocabulary for CONTEXT.md once this is accepted: **Verifier** and **Decomposer** (roles), **Verdict**, **Attempt**, **Briefing**, **Coordinator**. The Prover's definition loses "decides when to request review" alone and gains "after the Verifier passes it"; the Work log's gains verdicts and attempts.
- Reversing this means removing the Verifier gate, the briefing builder and the Coordinator; every event they write is one more kind in the work log, and the map, the snapshots and the decisions are untouched.
