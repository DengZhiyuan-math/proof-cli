# Store candidate proof text as files in a Markdown proof vault

**Status**: accepted

Every other piece of proof-cli state — theorem contracts, obligations, blockers, collaboration records — lives in SQLite or a JSON side file under `.proof/`, per the project's local-state-first convention. A Candidate proof's actual text is different in kind: it is long-form mathematical writing that a researcher wants to read, edit, and diff with their own tools, and the project explicitly asked for it to be usable as an Obsidian vault. Storing it as a string field in a SQLite row (the pattern used for `MemoryArtifact.content`, say) would work for the system but would hide the content from every editor, diff tool, and note-taking workflow a mathematician already uses.

Decided: Candidate proof text is stored as plain Markdown files under a new top-level `proofs/` directory — the **Proof vault** — kept separate from `.proof/` (which stays reserved for internal, non-human-authored state). Each submission writes a new, never-overwritten file, `proofs/<node-id>/v<N>.md`; this makes revision history a filesystem fact rather than something reconstructed from git log, which matters because the revise loop (ADR-0002) requires every prior attempt to stay queryable as immutable history. Each file carries its own opaque id in YAML frontmatter, and that id — not the file's path — is what `ReviewRecord.object_id` references, so a review stays attached to its submission even if the file is later renamed or moved within the vault.

The proof map node itself (id, kind, dependencies, and the lifecycle derivation from ADR-0002) stays in SQLite, in a new `candidate_proof_index` table (`node_id, version, file_path, is_current, review_record_id`) rather than in `.proof/collaboration.json` — it sits alongside `theorem_contracts` and the other core-model tables because it is core-model state (which version is current, what a node's lifecycle derives to), not collaboration/publication state. Only the proof's text moves to the vault; nothing else about node identity or the dependency graph does.

This is a deliberate deviation from the project's SQLite/JSON-first default, chosen specifically because the content in question is meant to be read and written directly by a person, not just by the CLI. It is hard to reverse once researchers have proof text spread across a growing vault of files with their own editor history and Obsidian configuration on top of it.
