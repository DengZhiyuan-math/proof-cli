# DAG is canonical, tree is explanatory, fog lives outside the graph

**Status**: accepted; amended by ADR-0011 (a local node's page is its LaTeX studio; an imported result has its own page)

A throwaway prototype (issue #10, `prototype/proof-map-ui` branch, published as a Claude Artifact) tested whether the domain model settled in ADR-0001 through ADR-0007 actually reads as a proof map a mathematician can use — not whether it looks good, but whether it answers, at a glance: how is the main theorem decomposed, what's already proven, what's in progress, what's ready for an agent right now, and what's blocking everything. Three decisions came out of building and looking at it.

**DAG is the canonical view; tree is a rooted explanation, not a second source of truth.** Real proof structure has shared dependencies — the prototype's `Claim C1` is depended on by both `Lemma A` and `Lemma C`, a genuine diamond. A tree forces a choice: duplicate the shared node under every parent, or silently pick one path and hide the other. Rendering it as a DAG avoids the choice entirely and is the default view. A tree view still earns its place, but for a different question — "how is `T` proved?" — where deliberately duplicating a shared node at every place it's used (marked as shared, pointing back to the DAG) is exactly what makes one path legible top to bottom. Tree is derived from the DAG on demand, rooted wherever the reader clicks; it is never the canonical structure.

**The frontier is the primary visual signal, not the status axes.** Workflow, acceptance, and integrity state (ADR-0004) all matter, but they're secondary information a reader checks once they know where to look. What a researcher — or an agent scanning for its next task — needs first is "what can I work on right now": nodes with no unresolved dependency and no active claim. The prototype gives frontier nodes the strongest available treatment (a distinct accent border and an explicit "ready for agent" tag) independent of whatever encoding the other three status axes use, so it survives regardless of how those get styled.

**Proof fog stays outside the graph, as its own list, never a graph node.** A fog item is by definition not precise enough to be a Claim yet — giving it a node would either force a premature, fake-precise statement into the model, or require a special "vague" node kind that every graph operation (dependency, frontier, Acceptance) then has to special-case. Instead fog is a flat, separate list next to the graph; when an item becomes precise enough to state and depend on, it **crystallizes**: a new Claim node is created (an ordinary node-creation, not a migration of the fog item itself) and the fog entry is dropped. Nothing about the graph model needs to know fog exists.

These three are genuine trade-offs made after trying the shape, not the obvious path (a tree would have been the simpler default to build; fog-as-a-node would have been the simpler model to implement), and reversing any of them means redoing both the visualization and, for the first two, re-litigating how the graph itself is read — hence an ADR rather than a prototype note.

**Update (spec #136, decided in #125):** a fog item's record is a row in the project's SQLite (`proof_fog`), written only through `proof fog …` and the proof map page, with a vault folder `proofs/fog/<fog-id>/` implied by its id and created only when something — an Experiment's files — is put there: the ADR-0003/0010 pattern of a SQLite record with vault files, not a file per item. Anyone, agents included, may add, edit or drop an item (with a reason; reversible): fog is not a mathematical judgment. An item may be *near* nodes, an informal pointer that touches no node's state.

**Update (spec #136, decided in #126, #128):** "the fog entry is dropped" above means it *leaves the fog list*, not that it is deleted. A crystallized item reads `crystallized`, names the Claim it became (a single-child Split of the parent when there is one, every Split rule kept; the statement written then, never taken from the item's text), and keeps its text, notes, near nodes and Experiments — the numerical runs recorded against it, which never changed its status and never become an Evidence check. `ProjectState.failed_routes` is frozen as legacy; `project analyze` reads the last dropped item instead.

**Update (ADR-0011, #70):** the map page is the researcher's one entry, and where nodes are created. _(Update, PR #107: the page's New node form was removed; nodes are created from the CLI with `proof node create`. The rest of this note still holds.)_ Clicking a theorem, lemma or claim opens its **studio**: editor, compile, PDF with SyncTeX, the proof agent, and a node panel for claim, split, request review, Challenge, Evidence check and the node's Review decisions. Clicking an imported result opens its own page, with its source, dependents and Reference review. The three views above (DAG, tree, fog) are unchanged.
